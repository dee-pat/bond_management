# Bond Management Migration

Change shape in _expand/contract_ phases so every deployed site migrates safely, then retire what is left behind.

## Sources of truth

- [AGENTS.md](../../../AGENTS.md) "App-specific migrations and permissions" owns patch, index, DocPerm, and `after_install` rules.
- [migration-lifecycle.md](../../../docs/specs/migration-lifecycle.md) owns the registered-patch regression on a temporary site, its representative legacy data, and cleanup.
- [verification.md](../../../docs/verification.md) owns gates and evidence; [domain-model.md](../../../docs/domain-model.md) must change with any DocType, `Link`, or `Table` change.

## Pick the branch

- **Additive** (new DocType, field, index, DocPerm): normal Frappe migrate handles schema; add a patch only for data or an invariant, and bootstrap invariants in `after_install` too. Model sync drops manual indexes that DocField metadata cannot declare, and re-importing a changed DocType JSON replaces its DocPerm rows with the JSON's, so also reapply manual indexes and patch-managed DocPerms idempotently from `after_migrate`; a logged patch never runs again. A new field with a default on an existing Single DocType is one schema exception: sync stores no `tabSingles` value and defaults apply only when the Single has no stored values at all, so established sites read `None`. Backfill a business default with an idempotent data patch and test it on a populated site. A new `unique` field is another: model sync adds it as `ADD COLUMN ... UNIQUE` with its default, which fails on a populated table for NOT NULL types (`Check`, `Int`, `Currency`, `Float`, `Percent`) or any field with a default. If the field is nullable with no default (for example `Data` or `Link`), sync's `ADD COLUMN ... UNIQUE` succeeds on a populated table and previous-release workers insert `NULL`, which a MariaDB unique index allows more than once, so declare `unique` in the same release. Otherwise ship it in release N without `unique` and with nothing relying on its uniqueness yet, because controller validation alone is a check-then-insert race; previous-release workers insert the column default, so in release N+1, after no pre-N writer can run, backfill distinct values, check for duplicates, and install an idempotent manual unique index from the patch, `after_install`, and `after_migrate` (sync drops a unique index the DocField does not declare). Set the DocField `unique` flag only in a later release, and cover the ordering with a populated lifecycle case. If the deployment stops every previous-release worker before migrate, N and N+1 can be one release. A new `reqd` field on a populated DocType without a usable default is a third exception: sync adds the column empty and existing documents then fail mandatory validation on save. Ship it optional in release N with every server writer populating it; in release N+1, after no pre-N writer can run, backfill it in an idempotent `[post_model_sync]` patch, set `reqd`, and verify populated legacy rows. As with `unique`, N and N+1 can be one release only if the deployment stops every previous-release worker before migrate.
- **Tighten an existing field** (non-unique to unique, optional to required): stage the change across releases, with populated lifecycle coverage for each transition.
  - **Unique:** in release N, keep `unique` disabled, update every writer to produce distinct values, and keep all code independent of the uniqueness invariant; controller checks alone still race. In release N+1, after all old writers that can create duplicates are drained and cannot return through rollback, clean legacy duplicates with an idempotent data patch, verify no duplicates remain, then install the database constraint. Keep the DocField `unique` flag disabled during that cleanup release so model sync cannot install the constraint before the data patch. Install an idempotent manual unique index from the patch, `after_install`, and `after_migrate`; enable the DocField flag only in a later release. Code may rely on uniqueness only after cleanup and database enforcement succeed.
  - **Required:** in release N, keep the field optional while updating every writer to populate a usable value. In release N+1, after all old writers that can omit it are drained and cannot return through rollback, backfill existing empty values with an idempotent data patch and verify every existing row has a usable value. Only then enable `reqd` in a later release.
- **Rename** (DocType or field): one release, one patch, see _Renames_, only when the deployment stops every previous-release worker before migrate and a rollback restores the pre-migrate backup. Otherwise old and new code write different columns or query a renamed table, so treat the rename as a retype and use _Expand/contract_.
- **Remove or retype** (field, DocType, `Link` target, `Table` ownership): expand/contract across releases, see _Expand/contract_.
- **Retire** (one-time patch, deprecated path, dead code): see _Retirement_.

## Renames

The two renames run on opposite sides of model sync, each in a patch whose rerun is a no-op:

- **DocType:** `frappe.rename_doc("DocType", old, new, force=True)` in a `[pre_model_sync]` patch, so the table and links move before the renamed JSON syncs. `rename_doc` loads the old DocType first and raises when it is gone, so guard on existence: rename when only the old exists, skip when only the new exists, and throw when both or neither exist. Test a forced rerun. `DocType.after_rename` skips renaming files and folders while `frappe.flags.in_patch` is set, so rename the module folder, JSON, controller, test files, and controller class in the repository in the same change.
- **Field:** `frappe.model.utils.rename_field.rename_field(doctype, old, new)` in a `[post_model_sync]` patch. It requires the synced DocType and silently returns when the new field is missing, so a pre-sync call copies nothing. It copies every row into the new column with an unconditional `UPDATE`, and Frappe leaves the old column in place, so a forced rerun (the lifecycle `requeue()` deletes Patch Logs) overwrites values the app has since written with stale legacy ones. Patch Log is not a guard: skip the call when a durable marker says the copy already ran, for example a namespaced `frappe.db.set_global` key that cannot match a fieldname, set in the same patch after the copy. Test that a forced rerun after editing the new field on a migrated row keeps the edit. A renamed `unique` field hits the same sync failure as an additive one (see _Pick the branch_): stage it the same way. For a `Table` or `Table MultiSelect` field, do not call `rename_field`: the parent table has no column, so default validation returns early, and with `validate=False` it updates `parentfield` without a `parenttype` predicate, moving the children of every parent that reuses the child DocType. Update the child table where `parenttype` is this DocType and `parentfield` is the old name (a rerun matches nothing), call `update_property_setters` from the same module if any exist, and test that the children load under the new field while another parent's children stay attached. For an `Attach` or `Attach Image` field, `rename_field` leaves `File.attached_to_field` on the old name, and a later private/public change writes the new URL through that stale name; in the same patch update `File` rows for this DocType from the old fieldname to the new one (idempotent by its `WHERE`) and test a private attachment.

Verify the migrated business data on representative legacy rows, not just the absence of errors. Then update every reference in the same change: controllers, `utils/`, `hooks.py` (`_financial_doctypes`, permission hooks, `doc_events`), `api/investor*.py` projections, reports, Desk JS, the SPA, tests, factories, the Playwright seed, and domain-model.md. Done when `git grep` for the old name returns only the patch and its lifecycle fixtures and assertions, and `git ls-files` lists no path containing its snake_case form.

## Expand/contract

Frappe has no down migration: rollback is restoring the pre-migrate backup. Keep each release valid for both the previous and next code.

1. **Expand,** release N. Add the new field/DocType alongside the old one. Write both from the server, but keep reading the old one: it stays authoritative while previous-release workers, or a code-only rollback, can still write only the old shape.
2. **Migrate,** release N+1, after every deployed site runs N and no pre-N writer can run. A registered, idempotent, batched patch backfills the new shape from the old, catching rows that only old code wrote. Add its legacy rows to the lifecycle fixtures and test results as business data (amounts, `Decimal` precision, provenance), not only row counts.
3. **Switch,** in the same release N+1. Read only the new shape; keep writing both, because release-N workers or a rollback to N still read the old one.
4. **Contract,** in a later release after every deployed site ran step 2 and no release that reads or writes the old shape can still run (release N+1 still writes it, so it too must be drained and no longer a rollback target), stop writing it and remove it:
   - **Field:** delete it from the DocType JSON. Frappe leaves the database column in place; `bench trim-tables` drops orphan columns.
   - **DocType:** first move or delete what still references it (`Link` and `Table` fields, User Permissions, DocShares, attached Files, reports, workspace entries, `_financial_doctypes` and other `hooks.py` entries), then delete its module folder. `bench migrate` removes the orphan `DocType` record but keeps the table; `bench trim-database` drops it.
   - Both trim commands are destructive and site-wide (`trim-database` drops every deleted DocType's table, other apps' included). Run each with `--dry-run` per site, show the user the list, and run it for real only with their explicit approval, never on the persistent dev or test site as part of a routine gate.

Done when each release passes the lifecycle sequence and no code reads or writes the old shape.

## Retirement

A one-time data patch is retirable only after the user confirms every deployed site has run it and that no backup, staging copy, or offline site still supported for restore and upgrade predates it; such a site would upgrade without the transformation. If those restore paths stay supported, keep the patch registered. A fresh install marks it complete without running it. In one change: remove its `patches.txt` line and module, any `after_install`/`after_migrate` entry, its tests, its lifecycle fixtures and assertions, and the references in migration-lifecycle.md. Invariant patches (DocPerms, manual indexes) stay, because fresh installs and migrates both need them.

For deprecated code paths, find every consumer first (`git grep`, `hooks.py`, whitelisted method names called from Desk JS and the SPA, report JSON) and remove the path only when the count is zero. Done when nothing imports, routes to, or calls the removed name.

## Verify

A fresh install of the current tree creates only the new schema and marks every patch complete, so lifecycle `prepare()` must reconstruct the schema state for the release immediately before the migration under test. For a rename or retype, recreate the old shape (the old `DocType` record and its table, or the old column) with direct writes and DDL, load legacy rows into it, and assert it exists before the first migrate. For an additive field tested in release N, drop the new column and clear the DocType's `migration_hash` so the first migrate re-imports the JSON and performs the real `ADD`. For a staged field tested in release N+1, keep the column that release N introduced, but remove any manual index that `after_install` already created before seeding legacy values; then verify the N+1 backfill and index installation against that prior-release state. In particular, a staged non-null unique field must start with duplicate legacy/default values and no new unique index, so the test proves the backfill makes values distinct before the migration installs the index. Never let a fresh-install index prevent the legacy rows from being seeded. A Single DocType has no table: recreate the old `(doctype, field, value)` row in `tabSingles`, delete any new-field row, and assert the migrated business value. For a DocType rename, first remove the new `DocType` record and table, then assert only the old one exists, because the rename guard throws when both exist; otherwise the guards skip and the test passes without migrating anything.

For existing fields being tightened, lifecycle `prepare()` must restore the preceding release's metadata and database state: keep the field optional or non-unique, remove any new unique index before seeding duplicate legacy values, and seed empty values for requiredness. Cover each staged transition with populated rows, assert cleanup/backfill preserves the intended business values, and verify the constraint or `reqd` is enabled only after the data is valid. Assert duplicate writes fail once the unique constraint is installed, empty saves fail once `reqd` is enabled, valid writes succeed, and forced patch reruns preserve migrated values.

Run the lifecycle sequence for any patch change, plus the applicable gates from verification.md, and drop the temporary site afterwards whether it passed or failed.
